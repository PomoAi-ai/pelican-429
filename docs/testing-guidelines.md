# 测试与验证约定

本文是 `AGENTS.md` 中“测试”和“验证”两节的详细说明。

## 1. 现状

截至 2026-10，`test/` 目录共有约 2.9 万行代码、1281 个 `test(...)`，其中 597 处 `assert.throws`。也就是说，接近一半的断言只在验证“传入非法参数时会抛错”，而这些参数大多来自仓库内部、类型已经约束过（见 `docs/coding-guidelines.md`）。

这类测试给防御式代码提供了保护：删掉多余的守卫，测试就会失败，于是守卫越积越多。新代码不要延续这个模式。

## 2. 什么时候写测试

改动可逆、影响小，且测试只会复述实现时，不写测试。只有下面几种情况值得新增测试：

1. **修复 bug**：先写一个能复现缺陷的用例，修复后它应该通过。这是首选的测试类型。
2. **有分支的纯逻辑**：`world`、`physics`、`combat`、`entities`、`sim`、`core` 中可观察的行为，例如碰撞结果、生成出的地形或状态转换。
3. **确定性契约**：同一种子生成相同的世界；逻辑层不依赖时钟和随机数。
4. **边界校验**：`validateTuning`、`parseSeed`、设置解析。每类非法输入写一个代表性用例即可，不要穷举每个字段。

下面这些不要写：

| 不要写 | 原因 | 本仓库现有例子 |
|--------|------|----------------|
| 用 `readFileSync` 读取 `src/` 源码，再断言里面包含某段字符串或正则 | 测的是代码长什么样，不是它做了什么；重命名变量就会失败 | `test/tree-ride.test.ts` 中断言 `frame-loop.ts` 包含 `d.env.update(waterTime, worldDt, alpha);` |
| 断言常量等于它的字面值 | 只是把源码抄了一遍 | `contracts-013.test.ts` 中的 `TILE_TIMBER === 7` |
| 对内部参数逐项断言“非法时抛错” | 守卫本身不该存在 | 各 `render-*`、`minimap` 测试中的大量 `assert.throws` |
| 按任务编号或版本命名的测试文件或用例 | 任务结束后没人知道它在保护什么 | `contracts-013.test.ts`、`render-desert-rocks-v3.test.ts`、`architecture.test.ts` 中“011/012/013/014 新文件归入正确分层” |
| 断言 three.js 网格的顶点数、材质参数、uniform 名称 | 视觉调整一次就要改测试；它们无法证明画面正确 | 部分 `render-*` 测试 |
| 为了能在 Node 下测试，而在生产代码中加分支 | 见 `docs/coding-guidelines.md` §3.4 | `precip-sky.ts` 的 `getContext` 判断 |

渲染效果、动画手感和 UI 布局由人在浏览器中验收，不写自动测试。

## 3. 怎么写

- 优先在已有的同主题测试文件中添加用例。只有新增了一个模块时才新建测试文件，文件名使用模块名。
- 一个用例验证一个行为。用例名用中文描述行为，例如“玩家零血后不再移动”。
- 通过公开接口测试，不导出内部函数专门给测试用。
- 复用 `test/helpers/` 中的夹具，不复制粘贴构造代码。
- 不 mock 本仓库的纯逻辑模块。直接用真实的 `generateWorld`、`stepSim` 加小地图夹具。
- 断言具体的值，不写 `assert.ok(result)` 这类只要不报错就通过的断言。

## 4. 修改或删除已有测试

- 实现改动导致已有测试失败时，先判断：是行为真的变了（需求变更，更新测试），还是引入了回归（修代码）。不确定时停下来问用户，不要直接改断言让测试通过。
- 已有测试符合 §2 中“不要写”的类别时，可以在当前任务涉及的文件里删除，并在汇报中列出删了哪些、为什么删。不要为此单独发起大规模清理，除非用户要求。
- 禁止使用 `test.skip`、`test.todo`，也禁止通过注释掉用例的方式让测试“通过”。

## 5. 验证：运行多少

全量 `npm test` 需要约 60 秒。按改动范围选择命令：

| 改动 | 运行 |
|------|------|
| 只改文档或注释 | 不运行 |
| 改一个模块 | `npm run typecheck` + 与该模块对应的测试文件，例如 `node --test test/physics.test.ts` |
| 改公共模块（`core`、`config`、`world/tile-map` 等）或跨层改动 | `npm run typecheck` + `npm test` |
| 任务结束、准备交付 | `npm run typecheck` + `npm test` + `npm run build`，各运行一次 |

- 测试通过后，只有出现新的改动、失败或未解决的疑点，才扩大范围或重跑。
- 不写一次性的验证脚本或探针文件放进仓库。需要临时复现时，使用 `node --input-type=module` 从标准输入运行（参见 `task/001-review-project-health/REVIEW.md` 中的复现命令）。
- CI 不运行测试（用户全局规则）；以上命令只在开发机手工运行。

## 6. 汇报

交付时用一行列出实际运行的命令和结果。没有运行的检查要说明没运行，不要写“应该能通过”。
